## 总览（一页看懂）

### 这是什么

一套**面向财税领域的知识问答与方案生成系统**。它先把法规整理成"有版本、有效力、
可追溯"的结构化知识，再让检索结果带着出处回答——而不是把一堆 PDF 丢给大模型自由发挥。

### 它解决什么问题

通用大模型回答财税问题有三个致命伤，本方案逐条对症：

| 毛病 | 本系统的做法 |
|---|---|
| 编造条文 | 只引用库里真实存在的条文；引用对不上，整条答案作废 |
| 混淆时效 | 每条条文带生效区间与效力状态；已废止、待复核的一律进不了检索 |
| 说不出来源 | 每个结论都能点开原文，看到文号、发文机关与生效日期 |

### 一次提问的完整链路

```
用户提问
  → ① 事实抽取      口语 → 税种 / 主体 / 金额 / 地区 / 期间（缺什么就问，不硬答）
  → ② 三路召回      结构化精确 + 稀疏关键词 + 语义向量 → RRF 融合 → 重排
  → ③ 适用性判定    逐条检查适用条件，给出「适用 / 不适用 / 需确认」与理由
  → ④ 计算          金额、税率、期限一律由计算引擎算，不让模型心算
  → ⑤ 组装答案      六段式：判定 → 依据 → 计算 → 步骤 → 风险 → 说明
  → ⑥ 验证          引用真实性 / 时效 / 复算 / 合规；不过就修正、降级或转人工
```

### 八个层次

| # | 层次 | 做什么 |
|---|---|---|
| ① | 交互层 | 问答界面、税费计算器、筹划对比台、专家复核台、管理后台 |
| ② | 域路由层 | 判断问题属于哪个域、加载对应域包、决定输出模式 |
| ③ | 领域理解层 | 事实抽取、意图识别、槽位补齐、指代消解 |
| ④ | 领域推理层 | 适用性判定 → 政策筛选 → 计算 → 方案编排 |
| ⑤ | 知识与证据层 | 三路召回 + 效力硬过滤 + 交叉引用展开 |
| ⑥ | 域包层 | 本体 / 抽取器 / 检索策略 / 推理器 / 验证器 / 模板 / 评测集 / 术语表 / 风险规则 |
| ⑦ | 验证层 | 引用真实性、时效、计算复算、合规四类校验 |
| ⑧ | 数据层 | PostgreSQL（真相源）、Qdrant（可重建索引）、Redis、对象存储、Celery |

横切能力：答案模板引擎、自进化引擎、评测门禁、可观测性、权限与审计、成本控制。

### 五条关键设计

| 设计 | 一句话 |
|---|---|
| 域包架构 | 领域能力打包成插件，新增领域不改引擎代码（已有测试锁住） |
| 效力硬过滤 | 废止、待复核的条文在检索阶段就被拦住，不会占用召回名额 |
| 时点查询 | 同一问题问"2023 年"和"2025 年"，各按当时的法规口径回答 |
| 条文级版本 | 数据库层约束保证同一条文的生效区间不重叠 |
| 元数据不猜 | 文号、机关、日期抽不到就标记待复核，绝不编造 |

## 0. 设计定位与要点

### 0.1 系统回答问题的深度

用户问"公司买设备能不能抵税"时，系统给出的不只是政策原文，而是：

**适用条件判定 + 计算过程 + 办理步骤 + 依据条款（带文号与生效日期）+ 风险提示 + 时限**

**本质：不是"检索文字"，而是"代为推理并给出可执行方案"。**

### 0.2 财税知识的特殊性

| 域 | 知识形态 | 正确性要求 | 输出形态 |
|---|---|---|---|
| **财税** | 法规条文 + 效力状态 + 交叉引用 + 计算规则 + 流程 | 极高（引用废止文件=错误；算错=法律风险） | 判定 → 依据 → 计算 → 步骤 → 风险 |

这类知识有一个共同点，**和通用客服完全不同**：

> 答案的正确性不来自"文字像不像"，而来自**逻辑推导和计算**。
> 因此系统必须有"推理层"和"验证层"，不能只有"检索层 + 生成层"。

### 0.3 六个结构性设计

| # | 升级 | 为什么必须 |
|---|---|---|
| 1 | **域包（Domain Pack）架构** | 财税领域的知识结构、推理逻辑和输出格式都是专用的。引擎必须能"插卡"，否则每加一个领域都要重写系统 |
| 2 | **领域本体层** | 法条有"章条款项"和效力状态，这些结构不表达出来就用不上 |
| 3 | **领域推理层** | "给方案"必须靠推理：条件判定 → 计算 → 编排步骤。纯 RAG 做不到 |
| 4 | **验证层** | 涉及金额的答案必须用计算引擎复算。**这是本方案的信任基础** |
| 5 | **答案模板引擎** | 财税答案有固定的专业表达结构，格式本身就是专业性的一部分 |
| 6 | **筹划引擎** | 筹划不是"问答"而是"方案寻优"：检索 → 生成候选方案 → 量化测算 → 合法性审查 → 风险分级。见 4.10～4.14 |

### 0.4 一条重要的实施建议（先说结论）

**不要同时做两个域。先选一个域做到能商用，再复制到第二个域。**（✅ 已确认：先做财税）

理由：域包架构的价值必须由"第二个域能否低成本接入"来验证。同时开工的结果通常是两个都做不深。

**财税域先行的理由**：

- 知识边界清晰（法规是封闭的、可枚举的）
- 正确性可机器验证（计算引擎复算）
- 商业价值直接（省人力、降风险）


**关于"全税种"的一条工程建议（需要事先知晓）**：

全税种可以做到，但要分两层看，否则工期会失控：

| 层次 | 全税种是否可行 | 说明 |
|---|---|---|
| **知识层**（法规、政策、办事指引） | ✅ 立刻可行 | 导入即可，法规本身就覆盖全税种，工作量在解析与结构化 |
| **计算层、筹划层** | ⚠ 建议分批 | 我国税种约 18 个，加上各地优惠差异，逐税种建立可复算的计算规则与筹划手法库，工作量是知识层的数倍 |

**建议的分批方式（不是削减范围，而是排先后）**：

| 批次 | 税种 | 覆盖场景占比 | 说明 |
|---|---|---|---|
| 第一批 | 增值税、企业所得税、个人所得税（工资薪金）、附加税费、印花税 | 约 85%～90% 企业日常 | 计算与筹划能力先在这五个税种上做到"能用、能算、有依据" |
| 第二批 | 消费税、房产税、城镇土地使用税、土地增值税、契税 | 补充 | 涉及不动产与特定商品的场景 |
| 第三批 | 资源税、环保税、车船税、车辆购置税、耕地占用税等 | 长尾 | 按客户实际需求排期 |

**知识层全税种全覆盖 + 计算筹划层分批**，这样既满足"全税种"的要求，又不会因为要等齐 18 个税种而无法上线。

## 1. 需求重新定义与成功标准

### 1.1 系统是什么

**一个引擎，多个域包。** 对外表现为若干垂直领域的专业问答与办事系统。

```
        财税领域知识引擎（一个引擎）
   ┌──────────────┬──────────────┐
   │   财税域包    │  未来的域包…  │
   │  法规/计算    │  医疗/法律/…  │
   └──────────────┴──────────────┘
```

### 1.2 场景走查：系统应该回答成什么样

这一节是最重要的验收参照。**如果系统只能给"法条原文"或"最终答案"，就没有达到本方案的标准。**

#### 场景 A（财税）：用户提问

> "我们是一般纳税人，2026 年 9 月卖了 113 万的货，是小微企业，增值税怎么交？"

系统应当输出：

```
【一、情形判定】
你描述的情形属于：货物销售 + 一般计税方法。
公司为小型微利企业，不影响增值税税率，但可能影响附加税费优惠。

【二、可能适用的政策】
· 《中华人民共和国增值税暂行条例》第十二条（现行有效，2017 修订）
· 《财政部 税务总局关于……的公告》（2023 年第 X 号，2023-01-01 起施行）
⚠ 若涉及优惠政策，还需确认"所属行业""月销售额"两个信息

【三、计算过程】
不含税销售额 = 1,130,000 ÷ (1 + 13%) = 1,000,000 元
销项税额     = 1,000,000 × 13% = 130,000 元
应纳增值税   = 销项税额 − 当期可抵扣进项税额
（还需提供本期进项税额，才能给出最终应纳税额）

【四、办理步骤】
1. 开具发票（税率 13%）
2. 次月 15 日前完成申报（遇节假日顺延）
3. 渠道：电子税务局 → 增值税及附加税费申报
4. 需准备：销项明细、进项发票、财务报表

【五、风险提示】
· 未取得合规进项发票的部分不得抵扣
· 优惠政策的适用条件需逐条核对，不要默认适用
· 逾期申报将产生滞纳金（按日加收万分之五）

【六、说明】
本回答依据现行有效政策生成，具体口径以主管税务机关认定为准。
```

**注意两点**：系统不"猜"进项税额，而是明确告知缺什么信息（这是槽位机制在专业域的用法）；并且给出免责边界。

### 1.3 可验收的成功标准

#### 通用

| 指标 | 目标 |
|---|---|
| 首字延迟 P95 | ≤ 3 秒 |
| 完整答案 P95 | ≤ 12 秒（专业域答案更长，可放宽） |
| 引用可追溯率 | 100%（每个结论都能定位到来源） |
| 月度可用性 | ≥ 99.9% |
| 知识变更生效 | ≤ 60 秒 |

#### 财税域

| 指标 | 目标 | 说明 |
|---|---|---|
| **效力状态准确率** | **100%** | 绝不引用已废止文件。这是硬指标，一次错误即为事故 |
| 条款引用准确率 | ≥ 98% | 引用的条款确实存在且内容匹配 |
| 计算准确率 | ≥ 99.5% | 由计算引擎保证，不靠模型心算 |
| 方案完整性 | ≥ 90% | 是否包含时限、材料、渠道三要素 |
| 风险提示覆盖率 | ≥ 85% | 高风险问题是否给了提示 |
| 专家复核通过率 | ≥ 90% | 抽检样本中被专家认可的比率 |

#### 财税域 · 筹划模块专属指标

| 指标 | 目标 | 说明 |
|---|---|---|
| **方案合法性通过率** | **100%** | 输出的方案不得触碰红线清单（虚开、隐瞒收入、虚假申报等），一次都不允许 |
| **反避税检查覆盖率** | **100%** | 每个方案都必须经过"合理商业目的"与"实质重于形式"检查 |
| 节税测算准确率 | ≥ 99% | 筹划前后税负差额由计算引擎测算 |
| 风险分级准确率 | ≥ 90% | 专家抽检：系统标 🟢🟡🔴 与专家判断的一致程度 |
| 方案可落地率 | ≥ 80% | 被专家认可为"具备可执行条件"的比例 |
| **高风险方案误放率** | **0%** | 🔴 级方案不得未经专家复核直接输出给用户 |
| 依据完整性 | 100% | 每个方案都要给出条款级依据 |

### 1.4 明确不做

- 不做通用聊天机器人。没有知识依据时，明确说"不确定"并给出人工/专家入口。
- **不提供违法或踩线的"筹划"**。筹划可以做，但红线不可越：虚开发票、隐瞒收入、虚假申报、骗取税收优惠、阴阳合同、无实质经营的税收洼地操作，一律拒绝并说明原因、给出合规替代路径（见 4.11 红线清单）。
- **不越过执业资质边界**。是否能对外提供筹划建议，取决于是否有具备涉税专业服务资质的主体承担（见第 16 章 F1、F2）。
- **不输出未经专家复核的 🔴 高风险方案**。系统可以生成，但必须停留在专家复核台，不能直达终端用户（见 4.12）。

### 1.5 假设（如有不符请纠正）

| # | 假设 | 影响 |
|---|---|---|
| B1 | 首版只做财税域 | 工期安排 |
| B2 | 法规全文可合法获取并存库（如国家法律法规数据库、税务总局官网公开发布内容） | 若不能，改为只存条文摘要 + 外部链接 |
| B3 | 财税使用者是会计/税务人员或企业主，具备基本专业认知 | 决定答案的专业深度 |
| B4 | 系统不对外出具正式税务意见书，仅作辅助决策 | 法律责任边界 |
| B5 | 数据存放在国内服务器，LLM 优先用境内模型 | 合规 |

### 2.2 与通用客服系统的差别

| 维度 | v2（电商客服版） | v3（专业域版） |
|---|---|---|
| 系统定位 | 单场景客服 | 多域知识引擎，可插拔域包 |
| 知识结构 | 知识单元（扁平） | 领域本体：法条层级 / 知识树层级 |
| 正确性来源 | 引用原文 | 引用原文 **+ 逻辑推导 + 计算验证** |
| 关键机制 | 混合检索 | 混合检索 **+ 结构化精确检索 + 推理 + 验证** |
| 输出 | 一段自然语言 | 结构化专业格式（模板引擎） |
| 时效处理 | 有生效日期字段 | **时间点查询**、效力状态强制校验 |
| 失败处理 | 拒答 / 转人工 | 拒答 / 转专家 / 给出"需补充信息"清单 |
| 评测 | 单一测试集 | 分域测试集 + 域特有硬指标 |

### 2.3 一次财税问答的完整链路

```
用户："我们是一般纳税人，9月卖了113万的货，小微企业，增值税怎么交？"
  │
  ① 域路由：识别为「财税 / 增值税 / 一般计税」
  │
  ② 事实抽取：
       纳税人身份=一般纳税人，税种=增值税，交易=货物销售，
       含税金额=1,130,000，期间=2026-09，企业规模=小型微利
       缺失信息：本期进项税额 ← 记录为待补槽位
  │
  ③ 政策检索（三路并行）：
       a) 结构化检索：按"增值税 + 一般计税 + 货物销售"命中条款集合
       b) 效力过滤：剔除已废止/未施行版本，只留生效区间覆盖今天的版本
       c) 向量检索：召回优惠政策、相似案例、常见问答
  │
  ④ 适用性判定：
       逐条检查优惠政策的适用条件（行业/规模/期间/地区）
       → 命中 1 条可能适用 + 标记 1 条需确认
  │
  ⑤ 计算（调用计算引擎，不让模型心算）：
       不含税销售额 = 含税 ÷ (1+税率)
       销项税额     = 不含税 × 税率
       → 返回结构化结果与公式步骤
  │
  ⑥ 方案编排（答案模板）：判定 → 依据 → 计算 → 步骤 → 风险 → 免责
  │
  ⑦ 验证层：
       · 引用的条款是否真实存在且现行有效 ✓
       · 税率与公式是否与命中条款一致 ✓
       · 计算结果复算一致 ✓
  │
  ⑧ 输出 + 落库（记录引用、计算过程、耗时、成本）
  │
  ⑨ 反馈钩子：用户是否追问进项税额 → 进入知识缺口分析
```

## 3. 域包（Domain Pack）架构

### 3.1 为什么这是最重要的设计

如果把某个领域的专属逻辑直接写进主流程，那么：

- 加第三个领域（法律、医疗、制造工艺）时要改核心代码，风险高
- 两个领域的改动互相影响，测试量暴增
- 无法给不同客户只开放某个域

**域包架构的作用**：把"领域知识"和"引擎能力"分开。引擎提供检索、推理调度、验证调度、模板渲染、评测、自进化这些通用能力；每个领域把自己的"结构定义、处理逻辑、校验规则、输出格式"打包成插件。

> 类比：引擎是一台电脑，域包是不同行业的软件。装财税软件就是财税系统，装医疗软件就是医疗系统。

### 3.2 域包的九个组件

| # | 组件 | 作用 | 财税域实例 |
|---|---|---|---|
| 1 | **本体 Schema** | 定义该域的知识结构 | 法规层级：法/条例/办法/公告/批复；效力：现行/修订/废止 |
| 2 | **抽取器** | 把原始资料转成结构化知识 | 条文切分（章条款项）、文号识别、生效/失效日期、发文机关 |
| 3 | **检索策略** | 该域的检索规则与权重 | 文号精确匹配优先、条款号检索、地域+层级过滤、**效力强制过滤** |
| 4 | **推理器** | 该域的问题解决逻辑 | 条件判定树 + 政策筛选 + 计算编排 |
| 5 | **验证器** | 该域的正确性校验 | 计算引擎复算、条款存在性、时效校验 |
| 6 | **答案模板** | 输出结构与专业格式 | 判定→依据→计算→步骤→风险→免责 |
| 7 | **评测集** | 该域的黄金测试集 | 税种 × 情形 × 时间 矩阵 |
| 8 | **术语表** | 同义词、简称、历史名称 | "小规模纳税人"↔"小规模"；政策简称 |
| 9 | **风险规则** | 该域的特殊约束 | 涉及金额/申报口径必须带免责；不碰筹划 |

**这九个组件都用配置文件 + 数据表达，不写死在代码里。** 新增领域 = 新增一个域包目录，引擎不改。

### 3.3 域包注册与加载

```
域包目录（示意）
domains/
  └─ finance_tax/          ← 财税域包（当前唯一的域包）
       ├─ manifest.yaml      （元信息：名称、版本、依赖、启用的角色）
       ├─ ontology.yaml      （本体 Schema）
       ├─ extractor.yaml     （抽取规则与 Prompt）
       ├─ retrieval.yaml     （检索策略与权重）
       ├─ reasoner.yaml      （推理链定义）
       ├─ verifier.yaml      （验证规则、计算引擎绑定）
       ├─ templates/         （答案模板）
       ├─ glossary.csv       （术语表）
       └─ eval_cases/        （评测集）
```

**加载规则**：

- 服务启动时读取所有域包的 `manifest.yaml`，注册到域路由表
- 域路由先判断"属于哪个域"；判断不确定时向用户澄清（"你是想问政策办理，还是税务计算？"）
- 每个域包可独立启用/停用、独立版本化、独立灰度
- 域包版本与引擎版本解耦：升级引擎不必改域包

### 3.4 多域之间的共享与隔离

| 项 | 处理 |
|---|---|
| 数据存储 | 表共享，用 `domain_id` 隔离（同一套 PG，不同域数据互不干扰） |
| 向量集合 | 共享集合，用 `domain_id` 过滤；跨域提问时分别检索再合并 |
| 通用能力 | 检索、Rerank、会话、评测、自进化、审计全部共享 |
| 特有逻辑 | 只在域包内，不污染引擎 |
| 术语表 | 域内有效，不跨域 |
| 租户与域的关系 | 一个租户可订阅多个域（当前只有财税域） |

### 3.5 新增一个域的完整清单（SOP）

将来加"法律"或"医疗"域时，照这张表做即可：

1. 定义本体 Schema（这个域的知识是什么结构）
2. 写抽取器配置（怎么从原始资料变成结构化知识）
3. 定检索策略（哪些字段要精确匹配、什么必须有过滤）
4. 定义推理链（这个域"解决问题"的逻辑步骤）
5. 接验证器（这个域的答案怎么机器验证）
6. 设计答案模板（专业输出格式）
7. 建术语表（同义词、别名、历史名称）
8. 建评测集（至少 200 条，覆盖主要情形）
9. 定风险规则（哪些问题不能答、哪些必须加免责）
10. 导入首批知识 → 跑门禁 → 灰度上线

**预估**：引擎成熟后，新增一个域约 4～8 周（不含知识导入与专家校验时间）。

## 4. 财税域设计（第一个样板域）

### 4.1 法规的结构化模型

财税知识不能按"文档 + 文本块"存，必须按法规自己的结构存。

#### 效力位阶（决定"谁大谁小"）

| 位阶 | 类型 | 示例 | 效力 |
|---|---|---|---|
| 1 | 法律 | 《中华人民共和国税收征收管理法》 | 最高 |
| 2 | 行政法规 | 《增值税暂行条例》 | 次之 |
| 3 | 部门规章 | 财政部/税务总局 令 | 再次 |
| 4 | 规范性文件 | 财税〔20XX〕XX 号、税务总局公告 | 具体执行口径 |
| 5 | 地方性法规/文件 | 各省实施办法、地方口径 | 仅本地有效 |
| 6 | 批复/答复 | 对特定问题的答复 | 个案适用，参考价值 |

**用途**：当同一问题有多份文件规定不一致时，按位阶判断优先级；并在答案中说明依据的层级。

#### 条文粒度（精确到"款""项"）

财税引用的最小单位往往不是"第 X 条"，而是"第 X 条第 Y 款第（Z）项"。系统的引用必须能精确到这个层级，否则专业性不成立。

```
法规
 └─ 章
     └─ 节
         └─ 条      ← 最基本引用单位
             └─ 款  ← 自然段
                 └─ 项  ← （一）（二）（三）
```

引用格式示例：`《增值税暂行条例》第十二条第二款第（二）项`

#### 元数据字段（每条法规、每个条文都要有）

| 字段 | 说明 | 示例 |
|---|---|---|
| 文号 | 唯一标识 | 财政部 税务总局公告 2023 年第 X 号 |
| 标题 | 正式名称 | 关于……的公告 |
| 发文机关 | 谁发的 | 财政部、国家税务总局 |
| 发布日期 | 公布日 | 2023-08-01 |
| 施行日期 | 生效日 | 2023-01-01（可能早于发布日，追溯生效） |
| 失效日期 | 废止日 | 空 或 2027-12-31 |
| 效力状态 | 见下方枚举 | 现行有效 |
| 地域范围 | 国家/省/市 | 全国 |
| 适用税种 | 增值税/企业所得税… | 增值税 |
| 适用对象 | 一般纳税人/小规模/特定行业 | 小规模纳税人 |
| 来源 URL | 官方发布地址 | 可回溯 |
| 版本号 | 修订次数 | v3 |

#### 效力状态枚举（必须严格区分）

| 状态 | 含义 | 是否可用于回答 |
|---|---|---|
| `not_yet_effective` | 已发布、尚未施行 | ❌ 不可（除非用户问"未来变化"） |
| `effective` | 现行有效 | ✅ |
| `partially_repealed` | 部分条款失效 | ⚠ 逐条判断，失效条款不可用 |
| `repealed` | 全文废止 | ❌ |
| `superseded` | 被新文件替代 | ❌ 用新文件 |
| `draft` | 征求意见稿 | ❌ 不作为依据（可提示"拟修订"） |

**关键细节**：废止可以精确到"条""款"，即整部法规仍有效、但某几条失效。这一层不做，就会引用到已经失效的条款。

### 4.2 法规关系网（为什么比单纯检索强）

法规之间不是孤立的。把这些关系建出来，系统才能"顺藤摸瓜"地给出完整依据。

| 关系类型 | 含义 | 用处 |
|---|---|---|
| `based_on` | 上位法依据 | 回答时给出"依据链"：条例 → 公告 → 口径 |
| `implemented_by` | 由某文件细化执行 | 让答案更具体（条例说原则，公告说标准） |
| `amended_by` | 被修订 | 找最新版本 |
| `repealed_by` | 被废止 | **防止引用废止文件** |
| `supersedes` | 替代了谁 | 追溯历史处理方式 |
| `references` | 引用了哪条 | 展开交叉引用，避免"看不懂" |
| `excepted_by` | 例外规定 | 特殊情形处理 |
| `localized_by` | 地方实施办法 | 地域差异 |

**实现方式**：PostgreSQL 关系表存这些边，不引入图数据库（见 ADR-0009）。查询时按关系展 1～2 层，避免无限扩散。

### 4.3 时效机制：时间旅行（财税域最关键的能力）

**问题**：用户问"2024 年 3 月我们那笔业务该怎么处理"，但系统里只有最新规定。直接按现行规定回答就是错的。

#### 数据模型：每个条文版本带生效区间

```
条文版本表：regulation_article_versions
  article_id         条文本体标识
  version            版本号
  valid_from         生效起始日（含）
  valid_to           生效结束日（不含），空表示至今
  content            该版本的条文内容
  source_doc_id      来自哪份文件
  change_reason      修订原因
```

**区间必须左闭右开** `[valid_from, valid_to)`，避免同一天两个版本同时"有效"。

#### 三种查询模式

| 模式 | 用户问法 | 查询逻辑 |
|---|---|---|
| **现行查询** | "现在怎么规定的" | `valid_from ≤ 今天 < valid_to` 且 `status = effective` |
| **时点查询** | "2024 年 3 月时怎么规定的" | `valid_from ≤ 2024-03-xx < valid_to` |
| **变更查询** | "这个规定什么时候改的、改了什么" | 取该条文所有版本，按 valid_from 排序对比 |

#### 强制校验（不可绕过）

```
未通过效力校验的条款，一律不得进入答案生成。

校验项：
  ① 条文版本的状态可用（effective 或 partially_repealed 中的有效款）
  ② 时间区间覆盖用户问题所指时点（未指定则用今天）
  ③ 地域范围匹配用户所在地
  ④ 该条款未被 repealed_by 关系指向
```

**这是唯一一条"一票否决"的规则**：只要效力校验不过，答案就不能发布，降级为"需人工确认"。

#### 未来变化提示（加分能力）

若存在 `not_yet_effective` 的版本覆盖用户问题的时间区间，主动提示：
"注意：该规定自 2027-01-01 起将有调整，届时适用 X 条。"

### 4.4 从法条到可执行方案：推理链

**这是"不只给条文，而是给解决办法"的技术实现。**

#### 推理五步

```
第 1 步：事实结构化
   从用户描述中抽取要素 → 缺失的要素形成待补清单
   要素：纳税人身份、税种、交易性质、金额、时间、地区、行业、企业规模

第 2 步：候选政策召回
   a) 结构化检索：按"税种 + 适用对象 + 适用场景"命中候选条款集
   b) 效力过滤：剔除不可用版本（4.3 的强制校验）
   c) 语义检索：召回优惠政策、相似案例、常见问答
   d) 关系展开：沿 based_on / implemented_by 展开 1 层，补充配套文件

第 3 步：适用性判定（逐条，不是猜一条）
   对每个候选政策，逐条检查适用条件：
     条件成立     → 标为"适用"
     条件不成立   → 标为"不适用"（并说明不适用原因，这是专业性的体现）
     条件无法判断 → 标为"需确认"（提出具体待确认问题）
   → 输出：适用清单 + 不适用清单 + 待确认清单

第 4 步：计算与编排
   调用计算引擎完成金额计算（见 4.5），拿到公式与结果
   编排办理流程：事项 → 时限 → 渠道 → 所需材料

第 5 步：组装答案（按模板）
   判定 → 依据 → 计算 → 步骤 → 风险 → 免责
```

#### 为什么"不适用清单"也要给

用户通常会问"我这种情况能不能享受 X 优惠"。只回答"不能"没有价值；说明"因为你的行业不属于 Y 目录，所以不适用"才叫专业。这一条也直接支撑了 4.9 的评测指标"方案完整性"。

#### 口语到专业的转换示例

| 用户口语 | 结构化后 | 系统动作 |
|---|---|---|
| "我这店" | 个体工商户 / 小规模纳税人（需确认） | 反问确认纳税人身份 |
| "赚了 200 万" | 不含税销售额 200 万？含税？ | 反问确认口径 |
| "上个月的票" | 2026 年 8 月开具的发票 | 时间要素 |

### 4.5 计算引擎（财税可信度的技术保障）

**铁律：涉及金额、税率、期限的计算，一律由计算引擎完成，不允许 LLM 心算。**

大模型的算术错误率足以摧毁专业信任，而且它算错时还会写得很有自信。

#### 规则配置化

税种计算规则用配置表达，不写死代码：

```yaml
税种: 增值税
计税方法:
  一般计税:
    公式: 应纳税额 = 销项税额 - 进项税额
    销项税额: 不含税销售额 × 适用税率
    税率表:
      - 货物销售: 13%
      - 交通运输服务: 9%
      - 现代服务: 6%
  简易计税:
    公式: 应纳税额 = 不含税销售额 × 征收率
    征收率: 3%
优惠规则:
  - 名称: 小规模纳税人月销售额免税
    适用条件: [纳税人类型=小规模, 月销售额 <= 100000]
    效果: 免征增值税
    依据: 财政部 税务总局公告 2023 年第 X 号
    有效期: [2023-01-01, 2027-12-31]
```

**注意**：优惠规则本身也带有效期和依据文号——规则会过期，必须跟法规版本绑定。

#### 计算引擎的要求

| 要求 | 说明 |
|---|---|
| 可展示过程 | 不只返回结果，要返回"公式 + 代入 + 中间值"，前端才能展示计算过程 |
| 精确小数 | 用十进制计算（不用浮点），避免 0.1+0.2 类误差；金额按分处理 |
| 四舍五入规则 | 按税法规定（如保留两位小数） |
| 边界提示 | 临界值（如正好 10 万）要提示 |
| 可复算 | 每次计算留记录，可回放核对 |
| 规则版本化 | 计算时记录用的是哪一版规则，政策变了结果可追溯 |

#### 覆盖范围（分阶段）

| 阶段 | 覆盖 |
|---|---|
| 第一阶段 | 增值税（一般计税 + 简易计税）、附加税费 |
| 第二阶段 | 企业所得税（含小微企业优惠） |
| 第三阶段 | 个人所得税（工资薪金）、印花税 |
| 后续 | 按客户实际需求扩展 |

**策略**：宁可先只覆盖 2 个税种但做到准确，也不要 18 个税种都"大概能算"。

### 4.6 稽查流程建模

稽查流程本质是**判定树 + 检查清单**，不是"一段知识"。

#### 结构

```
稽查事项（如：发票专项检查）
  ├─ 触发条件（什么情况下会被查）
  ├─ 检查步骤（有序）
  │    步骤 1：调取资料（清单：账簿、凭证、发票、申报表…）
  │    步骤 2：核对（核对方法、判断标准）
  │    步骤 3：疑点确认（常见疑点、解释口径）
  │    步骤 4：处理（补税/罚款/移交的标准）
  ├─ 企业应对建议（分情景：确实有问题 / 无问题但有疑点）
  ├─ 时限与权利（陈述申辩期限、复议期限）
  └─ 依据条款（关联条文）
```

#### 与知识单元的差别

| 项 | 知识单元 | 稽查流程 |
|---|---|---|
| 形态 | 单条问答 | 有向流程 + 条件分支 |
| 检索方式 | 语义相似 | 按事项名称 + 阶段定位 |
| 输出 | 答案 | 分步骤引导 + 清单勾选 |

**实现建议**：流程用结构化 JSON 存（步骤数组 + 条件分支），前端渲染成可交互清单（"已准备 ✅ / 未准备 ⬜"），这比一大段文字有用得多。

### 4.7 财税答案模板

模板是专业性的外在表现。固定六段式：

```
【一、情形判定】   把用户的情况翻译成专业表述；指出还缺哪些信息
【二、政策依据】   文号 + 条款 + 生效日期 + 效力状态（现行有效）＋ 为什么适用
【三、计算过程】   公式 → 代入 → 结果；标明口径与假设
【四、办理步骤】   事项、时限、渠道、所需材料（四要素齐全）
【五、风险提示】   常见错误、易被质疑点、不适用范围
【六、说明】       免责表述 + 人工专家入口
```

**模板可配置**：不同问题类型（政策咨询 / 计算 / 办理 / 稽查应对）用不同模板。模板放在域包里。

### 4.8 合规护栏与责任边界

| 护栏 | 具体做法 |
|---|---|
| 区分解读与建议 | 只做"政策解读 + 合规办理指引"；"税务筹划"类问题一律转专家 |
| 强制免责 | 涉及金额、申报口径、优惠适用，答案必须带"以主管税务机关认定为准" |
| 不做确定性承诺 | 不说"你一定能享受"，只说"符合以下条件即可享受" |
| 高风险转人工 | 涉及重大金额、稽查争议、跨区经营等，自动提供专家复核入口 |
| 计算留痕 | 每次计算过程与依据版本留档，便于事后核对 |
| 时效声明 | 每条答案标注"依据截至 2026-09-29 的现行有效政策" |
| 建议升级 | 提供"升级人工复核"按钮，形成人机协作闭环 |

### 4.9 财税域评测集设计

**矩阵化覆盖**，避免只测简单题：

| 维度 | 取值 |
|---|---|
| 税种 | 增值税 / 企业所得税 / 个人所得税 / 印花税… |
| 情形 | 一般情形 / 优惠适用 / 边界临界 / 跨期 / 稽查应对 |
| 时间 | 现行 / 历史时点 / 政策变更前后 |
| 难度 | 直接查条款 / 需多条款组合 / 需计算 / 需判定条件 |

**规模建议**：起步 300 条，其中：

- 60% 需组合判断（不能只靠单条命中）
- 15% 是"历史时点"问题（专门测时效机制）
- 10% 是"已废止文件"陷阱（正确答案是拒绝引用）
- 15% 是"信息不足"问题（正确答案是提出待确认清单）

### 4.10 筹划引擎：本质是"方案寻优"，不是问答

系统需要提供筹划建议。这是本方案里技术上最特殊的一块，必须先讲清楚它和普通问答的区别，否则会按错误的方式去建。

| 维度 | 普通问答 | 筹划 |
|---|---|---|
| 输入 | 一个具体问题 | 企业画像（主体、业务、财务、目标、约束） |
| 过程 | 检索 → 生成 | 检索 → **生成候选方案空间** → 量化测算 → 合法性审查 → 风险分级 |
| 输出 | 一个答案 | **多个方案 + 对比表 + 每个方案的依据、效果、条件、风险** |
| 正确性标准 | 与资料一致 | 既要有法律依据，又要有可执行的实施条件，还要经得起税务机关质疑 |
| 失败模式 | 答错 | **给出违法方案**（后果最严重）、给出无法落地的方案、低估风险 |

#### 一条必须澄清的常识（决定产品怎么设计）

依法节税是纳税人的合法权利，**筹划本身不违法**。违法的是：虚构交易、隐瞒收入、无实质经营套取优惠这类行为。

这两者的分界点，在税法上主要落在三处：

1. **是否有合理商业目的**（不只是为了少缴税）
2. **是否有真实业务实质**（不是纸面安排）
3. **是否违反具体条款的强制性规定**

所以系统的核心任务不是"想尽办法省钱"，而是**在合法边界内找最优解，并把这个边界明确告诉用户**。这条定位决定了下面的全部设计。

#### 筹划引擎的六段流水线

```
① 企业画像（结构化输入）
   主体：组织形式（有限公司/合伙/个体）、纳税人身份、行业、地区、规模
   业务：业务模式、交易结构、收入成本构成、供应链关系
   财务：收入、成本、利润、资产结构、薪酬结构、历史亏损
   目标：降低税负 / 递延纳税 / 合规整改 / 特定事项（股权转让、并购、重组）
   约束：风险偏好（保守/稳健/进取）、可调整弹性（能否改合同、改主体、改时点）
        │
② 筹划空间生成（三路来源）
   路径 A 政策适用型：扫描可享受但未享受的税收优惠（知识库 + 逐条条件匹配）
   路径 B 结构与安排型：从筹划手法库匹配（见 4.11）
   路径 C 时点与节奏型：收入确认、费用归属、折旧、亏损弥补的时点安排
        │
③ 候选方案生成
   每个方案 = 一组"具体动作" + 依据条款 + 前置条件 + 实施成本
   同一目标生成多个方案（保守/稳健/进取），便于对比
        │
④ 量化测算（必须调用计算引擎，见 4.5）
   筹划前税负 → 筹划后税负 → 节税额 → 实施成本 → 净收益
   支持多期测算（跨年、递延效果）
   ⚠ 不允许模型估算金额，全部由计算引擎产出
        │
⑤ 合法性审查（四道检查，见 4.12）
   依据检查 → 红线检查 → 反避税检查 → 实质检查
        │
⑥ 风险分级与输出（见 4.13）
   🟢 稳健 / 🟡 审慎 / 🔴 高风险 → 分级决定能否直接输出给用户
```

### 4.11 筹划手法库（新增的核心知识资产）

筹划能力不来自"读得多"，而来自**结构化的手法库**。这是财税域第二个必须新建的知识资产（第一个是法规库）。

#### 七类筹划手法

| 类型 | 典型手法 | 主要风险点 |
|---|---|---|
| **政策适用型** | 用足小微企业优惠、研发费用加计扣除、高新技术企业优惠、专项设备抵免 | 条件必须逐项真实满足，不得为享受优惠而虚构条件 |
| **主体架构型** | 组织形式选择（公司/合伙/个体）、总分机构安排、集团内分工 | 需有合理商业目的，不能仅为避税而拆分 |
| **业务模式型** | 业务拆分、合同安排、销售与服务的划分 | **高风险高发区**：必须与业务实质一致 |
| **时点安排型** | 收入确认时点、费用与损失的确认年度、亏损弥补顺序 | 有明确税法依据的时点选择合法；跨期人为操纵可能被调整 |
| **资产与投资型** | 折旧方法选择、资产重组、并购交易税务处理 | 特殊性税务处理条件严格 |
| **区域型** | 区域性税收优惠（特定园区/自贸区） | 必须有实质经营（人员、场所、业务），"注册即享受"风险极高 |
| **递延型** | 符合条件的递延纳税安排 | 需符合特定政策条件 |

#### 每个手法必须记录的六个字段

| 字段 | 说明 | 为什么必须 |
|---|---|---|
| 适用条件 | 逐条列明，可机器判定 | 决定方案是否适用 |
| 法律依据 | 到条款级，带生效区间 | 可追溯、可验证 |
| 节税机理 | 为什么能省钱（税基/税率/时点） | 让用户看懂，不是"玄学" |
| 风险等级 | 🟢🟡🔴 + 理由 | 决定输出方式 |
| **滥用边界** | 什么情况下会从"合法"变成"违法" | **这是最有价值的一条，也是普通资料里没有的** |
| 被否案例 | 已知的被税务机关调整或否定的情形 | 用真实教训约束方案生成 |

#### 手法条目示例

```
手法名称：小微企业增值税优惠适用
类型：政策适用型

适用条件：
  · 纳税人类型 = 小规模纳税人
  · 月销售额 ≤ 10 万元（或季度 ≤ 30 万元）
  · 开具的是普通发票（专票部分不适用免税）
  · 期间在政策有效期内

法律依据：
  · 财政部 税务总局公告 20XX 年第 X 号（有效期 2023-01-01 至 2027-12-31）

节税机理：直接免征增值税，属于税基归零型优惠

风险等级：🟢 稳健（政策明确、条件清晰）

滥用边界：
  · 为控制在 10 万以内而人为拆分合同、跨期调节开票时点 → 风险升为 🔴
  · 把本应开专票的业务拆成普票以享受免税 → 涉嫌虚假申报
  · 无真实业务的分拆（同一客户同一交易人为拆成多笔） → 红线

被否案例：
  · 某企业将单笔大额合同拆分为多份小额普票合同，被认定为不具有合理
    商业目的，追缴税款并加收滞纳金
```

**为什么要写"滥用边界"**：同一手法在合规使用和滥用之间只差一条线。把这条件明确写出来，系统才能在生成的方案里自动加上"这样使用是合法的，一旦 X 就变成违法"的提示。这正是用户真正需要的专业价值。

### 4.12 合法性审查与红线清单（筹划的安全阀）

每个候选方案在输出前必须通过四道检查，**任何一道不过，方案直接作废**。

| 检查 | 内容 | 实现方式 |
|---|---|---|
| **① 依据检查** | 是否有条款级法律依据？依据是否现行有效？ | 复用第 6 章引用验证器 + 时效验证器 |
| **② 红线检查** | 是否触碰红线清单？ | 规则匹配 + LLM 判定（红线清单见下） |
| **③ 反避税检查** | 是否具有合理商业目的？是否可能被特别纳税调整？ | 结构化论证模板 + LLM 初判 + 专家复核 |
| **④ 实质检查** | 是否有真实业务实质？是否有可提供的凭证？ | 要求用户确认业务真实性，并在方案中列出所需证明资料 |

#### 红线清单（命中即拒绝，不给方案）

| 红线行为 | 系统的处理 |
|---|---|
| 虚开发票（无真实交易开票） | 拒绝 + 说明该行为属违法 + 提供合规替代路径 |
| 隐瞒收入、账外经营 | 同上 |
| 虚假申报、伪造变造资料 | 同上 |
| 虚构条件骗取税收优惠 | 同上 |
| 签订阴阳合同 | 同上 |
| 无实质经营的"税收洼地"注册 | 拒绝 + 说明实质经营要求 + 指出合规做法 |
| 人为拆分交易以套用优惠 | 高风险警告 + 说明边界 + 转专家 |

**拒绝时的表达方式很重要**：不是冷冰冰地说"不能回答"，而是"这个做法属于 X 类违法风险，风险在于 Y，如果目的是 Z，合规的做法是……"。用户来找筹划，本质是想要合法的省钱办法，给出替代路径才是专业服务。

#### 反避税检查的落地方式（不做成形式主义）

"合理商业目的"是抽象标准，不能只让模型写一段话糊过去。做法是：

```
1. 系统提供论证框架（三道问句）：
   · 如果完全没有税收利益，这项安排还会做吗？
   · 这项安排是否带来了真实的经营效益（成本下降、效率提升、市场拓展）？
   · 是否有可验证的业务证据（合同、履约记录、人员、场地、资金流）？
2. 要求用户填写实际的商业理由（不能空着）
3. 系统基于用户填写内容做初判，给出风险等级
4. 🟡🔴 级方案强制进入专家复核（见 4.13）
```

**关键立场**：系统不替用户"编"商业目的。用户提供不了真实的商业理由，这件事本身就该是风险信号。

### 4.13 筹划方案的风险分级与输出控制

| 等级 | 判定标准 | 输出方式 |
|---|---|---|
| 🟢 **稳健** | 政策明确适用、条件清晰、税务实践中普遍认可、无争议口径 | 可直接输出给用户，附完整依据与实施步骤 |
| 🟡 **审慎** | 政策可适用但存在地区口径差异、执行细节需确认、可能被质疑 | 可输出，但必须标注"建议与主管税务机关沟通"，并提示专家复核入口 |
| 🔴 **高风险** | 依赖激进解释、存在被调整风险、可能触发反避税、滥用边界附近 | **不直接输出给用户**，只能进入专家复核台；由专家判断后决定是否以及如何给用户 |

#### 输出形态：多方案对比表（而不是单给一个方案）

| 方案 | 节税效果 | 依据 | 实施条件 | 风险 | 实施成本 | 建议 |
|---|---|---|---|---|---|---|
| 方案 A（政策适用型） | 约 X 元/年 | 公告 20XX 年第 X 号 | 需满足条件 1、2、3 | 🟢 | 低 | 推荐优先实施 |
| 方案 B（主体架构型） | 约 Y 元/年 | 企业所得税法第 X 条 | 需调整组织结构，周期 2 个月 | 🟡 | 中 | 建议先与主管税务机关沟通 |
| 方案 C（时点安排型） | 约 Z 元/年 | 实施细则第 X 条 | 需调整合同条款 | 🟡 | 低 | 可与其他方案组合 |

**每个方案还要给出**：

- 落地步骤（谁、什么时候、做什么）
- 需要准备的证明资料清单
- 如果被税务机关质疑，如何应答（这一点极大提升专业感）
- 组合建议（哪些方案可以叠加、哪些互斥）

#### 与专家复核台的交互

```
系统生成方案
   ├─ 🟢 → 直接给用户，同时抄送专家复核队列（事后抽检）
   ├─ 🟡 → 给用户（带提示），同时推送专家复核（限时确认，超时自动降级标注）
   └─ 🔴 → 只进专家复核台
             专家处理：放行（附说明）/ 修改后放行 / 驳回并说明原因
             驳回原因 → 进入评测集与手法库的"被否案例"
```

**专家复核台必须具备的能力**：

| 能力 | 说明 |
|---|---|
| 一屏看清方案 | 企业画像 + 方案 + 依据 + 测算 + 风险点，不用翻多个页面 |
| 快速判定 | 放行 / 修改 / 驳回，三个按钮 + 批注 |
| 一键修正 | 直接改方案文本与风险等级，系统记录差异 |
| 反馈入库 | 修正与驳回自动转为评测用例和手法库的负样本 |
| 工作量可视 | 待办量、平均处理时长（用于评估专家人力是否够） |

### 4.14 筹划专属评测集（用"被否方案"做负样本）

筹划的评测比问答难，因为它没有唯一正确答案，但有唯一"错误答案"——**违法或明显不可行的方案**。

| 样本类型 | 占比 | 说明 |
|---|---|---|
| 🟢 标准方案题 | 30% | 有公认的合规方案，检查是否给出 |
| 🟡 口径差异题 | 20% | 存在地区或执行差异，检查是否标注了不确定性 |
| **红线陷阱题** | **25%** | 用户直接要求违法做法，正确行为是拒绝 + 给替代路径 |
| 🔴 高风险识别题 | 15% | 方案看似合理但有滥用风险，检查是否正确分级 |
| 信息不足题 | 10% | 缺少关键信息，正确行为是提出补充清单而不是硬答 |

**负样本来源（关键）**：

1. 公开的税务稽查案例中被否定的安排
2. 内部专家在复核中驳回的方案
3. 用户尝试引导系统给出违法方案的话术

**评测执行**：筹划评测必须**全部经过内部专家人工判定**，不能只靠 LLM 裁判——因为红线判断事关法律责任。

## 5. 通用知识底座

### 5.1 存储分工（原则不变）

| 存储 | 存什么 | 是否真相源 |
|---|---|---|
| **PostgreSQL** | 法规、条文版本、知识树、题目、知识单元、版本、反馈、评测、审计 | ✅ 唯一真相源 |
| **Qdrant** | 向量 + 检索用 payload（域、租户、分类、状态、生效区间） | ❌ 可重建索引 |
| **Redis** | 会话上下文、热点缓存、限流 | ❌ |
| **OSS（S3 兼容）** | 原始文件（法规 PDF 等）、快照 | 原件源 |

> 对象存储统一走 **S3 协议**：私有化部署用 SeaweedFS（自建，Apache-2.0），云端可直接换阿里云 OSS / 腾讯云 COS，
> 只改 `S3_ENDPOINT` 与密钥，应用代码不变。原定的 MinIO 已于 2025 年下架全部社区镜像与二进制，
> 故本地与私有化默认改用 SeaweedFS，决策见 [ADR-0004](adr/0004-对象存储选型.md)。

**"向量库是可重建索引"这条原则**：财税法规会不断修订，索引必须能随时重建。任何时候从 PostgreSQL 都能重建出完整索引。

### 5.2 向量集合设计 v3

按 `domain_id` 维度区分不同领域，并把"知识单元"与"结构化条目"分开。

| 集合 | 内容 | 特殊 payload |
|---|---|---|
| `kb_knowledge` | 知识单元（通用） | `domain_id`, `subdomain`, `tenant_id`, `status`, `valid_from/to` |
| `kb_articles` | 结构化条文（财税条文） | `domain_id`, `article_id`, `article_no`, `effect_status`, `valid_from/to`, `region` |
| `kb_chunks` | 原文块（找原文用） | `doc_id`, `page`, `section_path` |
| `kb_cases` | 案例（财税案例） | `domain_id`, `question_type`, `tax_type` |
| `kb_history` | 历史问答（相似问题召回） | `conversation_id`, `domain_id` |

**命名向量**：`kb_articles` 与 `kb_knowledge` 同时挂 dense + sparse 两组向量（沿用混合检索设计）。

### 5.3 三路检索（含结构化精确检索）

两路（向量 + 稀疏）之外，再增加一路结构化检索——这是专业域的关键。

| 路 | 检索方式 | 解决什么 | 财税示例 |
|---|---|---|---|
| 1 | 结构化精确匹配 | 按编号/字段精确定位 | 文号、条款号、税种、地域 |
| 2 | 稀疏检索 | 精确词匹配 | 政策简称、专业术语、数字 |
| 3 | 稠密检索 | 语义相似 | "能不能抵"↔"进项税额抵扣" |

**融合方式（RRF）**：

```
三路并行召回（各 Top 20）
    ↓
RRF 融合（按排名，不用分数，避免量纲问题）
    ↓
结构化过滤（效力状态 + 时间区间 + 地域）
    ↓
Rerank 精排（Cross-Encoder）
    ↓
Top-K 进入推理层
```

**过滤必须放在融合之前还是之后？**

- **效力过滤必须放在检索前**（或作为硬过滤），避免已废止条款占用召回名额

### 5.4 随时增量（机制沿用 v2，补充专业域做法）

| 场景 | 生效目标 | 做法 |
|---|---|---|
| 单条法规修订 | ≤ 60 秒 | 新增条文版本，旧版本 `valid_to` 置为昨天；重建该条文向量 |
| 批量导入法规库 | 小时级 | Celery 分批处理，进度可视化 |
| 知识单元单条修改 | ≤ 60 秒 | 直接 upsert |
| 地方性法规批量入库 | 按批次 | 用集合别名做蓝绿切换 |
| 紧急下架错误知识 | ≤ 10 秒 | 状态置为 `disabled`，检索立即过滤，走软删除 |

**紧急下架是专业域必备能力**：一旦发现某条知识有错，要能立刻停用，而不是等下一轮发布。

### 5.5 容量与性能规划

| 域 | 数据量估算 | 向量条数 | 内存（int8 量化后） |
|---|---|---|---|
| 财税 · 国家层面法规 | 约 3～5 万份文件 | 约 50 万条（条文级） | 约 0.5 GB |
| 财税 · 地方 + 历史版本 | 约 10 万份 | 约 150 万条 | 约 1.5 GB |
| 财税 · 知识单元 + 案例 | — | 约 30 万条 | 约 0.3 GB |
| **合计** | — | **约 230 万条** | **约 2.5～3 GB** |

**结论**：单机 16GB 内存 + 3 节点集群（每节点 8GB 可用）即可支撑起步规模，无需过度设计。

**延迟预算（专业域答案更长，P95 ≤ 12 秒）**：

| 环节 | 预算 |
|---|---|
| 域路由 + 事实抽取 | 0.8 秒 |
| 三路召回 | 0.2 秒 |
| RRF + Rerank | 0.5 秒 |
| 推理 + 计算/符号验证 | 1.0 秒（计算类）；3 秒（复杂推导） |
| LLM 生成（流式） | 5～8 秒 |
| 验证层 | 0.3 秒 |

## 6. 验证层（信任基础）

### 6.1 为什么必须有这一层

普通客服答错了，用户顶多不满意。专业域答错了，后果是：

- 财税：错误申报 → 补税、滞纳金、罚款、信用降级

**"生成完就直接返回给用户"在专业域是不可接受的。** 必须有一层独立的、基于规则的校验。

### 6.2 四类验证器

| 验证器 | 检查什么 | 财税实现 |
|---|---|---|
| **引用验证器** | 引用的东西真实存在吗 | 文号存在、条款号存在、条文内容与引用一致 |
| **时效验证器** | 引用的东西现在还有效吗 | 效力状态 + 生效区间覆盖问题时点 + 地域匹配 |
| **计算/推导验证器** | 数字和逻辑对吗 | 计算引擎复算，与答案中的数字逐一比对 |
| **合规验证器** | 这样说有没有越界 | 高风险表述检查、免责声明是否齐全 |

#### 引用验证器的实现要点

这是最容易做也最有效的一环：

```
从生成的答案中抽取所有引用：
  财税：〔文号 + 条款号〕 模式匹配 + 语义抽取
        ↓
逐一到数据库核对：
  文号是否存在？ → 否 → 该引用无效 ❌
  条款号是否存在？ → 否 → 该引用无效 ❌
  条文内容与答案说法是否一致？ → 交由一致性检查（LLM 判定 + 关键词比对）
        ↓
任何引用无效 → 整条答案不通过
```

**为什么这条要一票否决**：引用错误是"编造依据"，比算错更严重，因为它伪造了权威性。

#### 时效验证器：财税的绝对红线

```
检查项：
  ① 答案中每个引用的条文，其版本状态在问题时点上是否为 effective
  ② 是否引用了 repealed / superseded 的版本
  ③ 是否引用了 not_yet_effective 的版本（除非明确说明"将施行"）
  ④ 涉及优惠政策的，是否标注了有效期

违反任一项 → 阻断输出
```

### 6.3 验证失败的处理流程

```
验证失败
   │
   ├─ 可自动修正（如：数字笔误、引用格式错）
   │     → 修正后重新验证 → 通过则输出
   │
   ├─ 需重新生成（如：引用了废止条款）
   │     → 带约束重新走一次推理与生成（最多重试 2 次）
   │
   └─ 无法恢复
         → 降级输出：
              财税：给出"已找到相关政策但需人工确认"，附上候选条款与专家入口
         → 同时记录失败样本（喂给评测集与自进化）
```

**关键原则：宁可说"不确定"，也不输出未通过验证的结论。**

### 6.4 验证记录

每次验证都留痕，用于分析与改进：

| 记录项 | 用途 |
|---|---|
| 验证了哪些项、通过/失败 | 统计各验证器的拦截率 |
| 失败原因分类 | 找出系统性问题（如总引用某份老文件） |
| 重试次数与结果 | 衡量推理稳定性 |
| 人工最终判定（抽样） | 校准验证器的严格程度 |

**验证层的指标也应被监控**：如"引用验证拦截率"，短期内上升说明知识库质量有问题，是重要的预警信号。

## 7. 答案模板引擎

### 7.1 为什么要独立成一层

| 只靠 Prompt 的问题 | 模板引擎的做法 |
|---|---|
| 格式不稳定，这次有步骤下次没有 | 固定段落结构，缺段会报错 |
| 无法按问题类型切换格式 | 政策咨询/计算/办理/稽查用不同模板 |
| 无法保证免责声明一定出现 | 免责段由模板强制渲染，不依赖模型 |
| 前端无法稳定解析渲染 | 输出结构化 JSON，前端按字段渲染 |
| 改格式要改 Prompt，容易破坏其他部分 | 改模板不动推理逻辑 |

### 7.2 模板结构

```json
{
  "template_id": "finance_tax.policy_calculation",
  "sections": [
    { "key": "judgement",  "title": "情形判定", "required": true },
    { "key": "basis",      "title": "政策依据", "required": true,
      "renderer": "citation_list" },
    { "key": "calculation", "title": "计算过程", "required": false,
      "renderer": "formula_steps" },
    { "key": "steps",      "title": "办理步骤", "required": false,
      "renderer": "ordered_steps", "require_fields": ["deadline", "channel", "materials"] },
    { "key": "risks",      "title": "风险提示", "required": false },
    { "key": "disclaimer", "title": "说明",     "required": true,
      "renderer": "fixed_text", "text": "本回答依据现行有效政策生成，具体口径以主管税务机关认定为准。" }
  ]
}
```

**两个关键约束**：

1. `required: true` 的段落缺失 → 视为生成失败，重试或降级
2. `renderer` 决定该段的渲染方式（引用列表、公式步骤、有序步骤），前端一致渲染

### 7.3 结构化输出而非纯文本

系统对内返回结构化 JSON，对外由前端渲染成可读界面：

| 段落 | 渲染形式 |
|---|---|
| 情形判定 | 文字 |
| 政策依据 | 可点击的引用卡片（文号 + 条款 + 效力状态 + 生效日期 + 查看原文） |
| 计算过程 | 公式 + 代入 + 结果（分步展示） |
| 办理步骤 | 编号列表 + 时限标签 + 材料勾选清单 |
| 风险提示 | 警示样式 |
| 说明 | 小字固定文案 |

**好处**：

- 财税用户可以直接核对"哪条哪款、什么时候生效"
- 支持导出（可导出为工作底稿）

### 7.4 流式输出与段落就绪顺序

专业域答案长，等全部生成完再显示体验差。建议：

```
先出"情形判定"（让用户确认理解是否正确）
   ↓
再出"政策依据"
   ↓
再出"计算过程"（如果需要补充信息，此处直接提问）
   ↓
最后出"办理步骤 + 风险提示 + 说明"
```

## 8. 自进化引擎

自进化沿用四条流水线（资料摄入、对话反哺、缺口发现、衰退淘汰），并补充财税域特有的机制。

### 8.1 四类流水线在专业域的调整

| 流水线 | 通用做法 | 本方案的调整 |
|---|---|---|
| **A 资料摄入** | 分块 → 抽知识单元 | 增加"**本体结构化**"：先按法条结构切分，再抽知识单元 |
| **B 对话反哺** | 从工单/客服对话提炼 | 从"专家复核通过的回答"提炼 |
| **C 缺口发现** | 低置信 + 未命中聚类 | 额外统计"哪些税种/情形问题最多但知识最少" |
| **D 衰退淘汰** | health_score 打分 | 以"法规效力变化"为主要触发器 |

### 8.2 财税域特有：法规变更监控（核心进化来源）

财税知识的过期不是因为"没人用"，而是因为**政策改了**。所以必须有主动的变更监控。

```
每日/每周任务：
  1. 监控官方发布渠道（财政部、税务总局、地方税务局）
     方式：RSS/公告页抓取 + 人工录入通道（双保险）
  2. 发现新文件 → 判断是否影响已有知识：
       ① 是否废止/修订了已入库的某条款？ → 触发相关性复审
       ② 是否新增了某场景的规定？       → 生成候选知识
       ③ 是否只是解读性文章？           → 归档，不作依据
  3. 受影响知识处理：
       条文 → 新建版本，旧版本设 valid_to → 失效条款自动退出检索
       知识单元 → 标记"依据已变更"，进复审队列
  4. 复审完成后跑门禁（第 8.3 节）→ 发布
  5. 生成"政策变化摘要"推送给订阅用户（这是额外的产品价值）
```

**"政策变化提醒"本身就是一个独立卖点**：企业最怕的就是"不知道政策变了"。

### 8.3 门禁升级为分域门禁（重要）

门禁按域设置，因为各域的"致命错误"不同。

| 域 | 一票否决项（必须 100%） | 常规指标 |
|---|---|---|
| 财税 | 效力状态正确率、引用真实存在性 | 计算准确率、方案完整性、风险提示覆盖率 |
| 通用 | 引用可追溯率 | 拒答准确率、延迟、成本 |

**一票否决的含义**：该项只要有一条不通过，整批发布阻断，不允许"整体指标达标所以放行"。

### 8.4 知识质量清单

入库前逐项检查，全通过才允许进入候选：

| 检查项 | 财税 |
|---|---|
| 来源可溯 | 文号 + 条款号 + 官方链接 |
| 时效明确 | 生效日期必填，失效日期建议填 |
| 内容完整 | 条件、例外、时限齐全 |
| 无重复 | 与既有条文/知识相似度 < 0.92 |
| 无冲突 | 与同条款其他版本不矛盾（除版本演进） |
| 专家校验 | 高风险条款需专家确认 |

## 10. 安全、权限与合规

RBAC、多租户隔离、PII 处理、审计、Prompt 注入防护沿用不变，并增加**角色化输出**与**专业责任边界**。

### 10.1 角色与权限（三角色 + 动态授权）

**结论先说**：财税首版只设三个角色——**管理员、审核专家、客户**。人员不写死，全部在后台动态创建，
由管理员分配角色与权限。唯一的例外是**固定管理员**：系统内置、拥有全部权限、不可删除也不可降权。

#### 三个内置角色

| 角色 | 一句话定位 | 默认权限 | 数据可见范围 |
|---|---|---|---|
| **管理员** | 管账号、管租户、发权限；**不参与业务审核** | 租户管理、用户管理、授权、审计查看、系统配置、重建索引 | 账号与审计信息；**默认看不到客户问答内容** |
| **审核专家** | 专业内容把关 | 法规/知识导入与审核发布、缺口处理、筹划方案复核（含 🔴 高风险放行） | 只看到**进入复核流程的那部分**客户数据 |
| **客户** | 用系统解决实际问题 | 提问、看答案与依据、税费计算器、保存底稿、导出、反馈 | 只有自己所属租户的数据 |

#### "动态管理"具体指什么

1. 新增人员 = 建用户 + 选角色，不写配置文件、不改代码。
2. 角色是**权限模板**；在角色之上，管理员还能给**单个用户**加权限或收权限（用户级覆盖）。
3. 典型用法：企业老板和会计都是"客户"角色，但给会计单独加 `calc.draft.save`（保存计算底稿）即可，
   不必为此新造一个"会计"角色。
4. 加角色是数据变更：以后要加"合规官"之类的角色，写一条数据即可，不动代码。

#### 与旧版 8 角色方案的关系

角色收敛为三个：原"知识管理员"并入**审核专家**，
原"企业用户 / 会计税务人员"并入**客户**（差异用用户级权限表达）。

### 10.2 专业责任边界（不可越过）

| 域 | 红线 | 系统行为 |
|---|---|---|
| 财税 | **可以提供筹划建议，但不得越过合法边界** | 四道检查全过才输出；命中红线则拒绝并给出合规替代路径（见 4.12） |
| 财税 | 不提供违法方案 | 红线清单（虚开、隐瞒收入、虚假申报、骗取优惠、阴阳合同、无实质经营套取优惠）一律拒绝 |
| 财税 | 🔴 高风险方案不直达用户 | 强制进入专家复核台，由专家决定是否及如何给用户（见 4.13） |
| 财税 | 不替用户编造商业目的 | 提供论证框架，要求用户填写真实理由；填不出即为风险信号 |
| 财税 | 对外提供筹划需有资质主体承担 | 见第 16 章 F1、F2；无资质主体时，筹划功能仅限企业内部使用 |
| 财税 | 不出具正式意见书 | 所有输出带免责声明；导出件带版本与时间戳 |
| 财税 | 不做确定性承诺 | 用"符合以下条件即可适用"而非"你一定能享受" |
| 财税 | 筹划方案必须留痕 | 企业画像、生成方案、测算过程、专家复核全部留存，可追溯 |

### 10.3 数据合规

| 项 | 措施 |
|---|---|
| 法规数据来源 | 记录来源与获取时间，尊重版权与转载规定 |
| 企业财税数据 | 用户输入的金额、税号等属敏感，加密存储、日志脱敏、按需留存 |
| 数据出境 | 优先境内模型与境内服务器 |

### 10.4 固定管理员与两级授权（不可绕过）

**固定管理员**是系统的"最后一把钥匙"，规则如下：

| 规则 | 内容 |
|---|---|
| 唯一性 | 全系统只有一个，数据库层面加约束，不允许出现第二个 |
| 不可变 | 不能删除、不能停用、不能降权、不能被其他账号修改密码 |
| 初始化 | 用户名与初始口令来自环境变量（`BOOTSTRAP_ADMIN_USERNAME` 等），首次登录强制改密码 |
| 兜底 | 忘记密码时，在服务器上执行重置脚本（`scripts/reset_admin_password.py`）；需要服务器权限本身即是最高门槛 |
| 使用场景 | 初始化、授予"审核专家"角色、授予业务审核类权限、应急处理；日常管理交给普通管理员 |

**两级授权**（防止管理员自己给自己加业务权限）：

| 谁 | 能授予什么 |
|---|---|
| **管理员** | 建租户、建用户、分配"客户"角色、授予**客户类与使用类**权限（见 10.5 的"可转授"列） |
| **固定管理员** | 上述全部 + 分配"审核专家"角色 + 授予知识类与筹划复核类权限 + 变更系统配置 |

**授权必须留痕**：每次授权/收权都记录 谁、在什么时候、给谁、加了什么权限、原因。
审计日志只增不改，界面上不提供删除入口。

## 11. 评测体系

### 11.1 分域评测集

| 域 | 规模 | 覆盖矩阵 | 特有硬指标 |
|---|---|---|---|
| 财税 | 起步 300 → 1000 条 | 税种 × 情形 × 时间 × 难度 | 效力状态 100%、引用存在性 100% |
| 财税 · 筹划 | 起步 200 → 600 条 | 税种 × 企业类型 × 风险层级 × 红线陷阱 | 红线拦截率 100%、高风险方案误放率 0% |
| 通用 | 100 条 | 跨域、模糊提问、恶意提问 | 拒答准确率 ≥ 95% |

### 11.2 评测的四个维度

```
① 事实正确性：答案内容对不对
② 依据正确性：引用的条款真实且有效
③ 过程正确性：推理步骤、计算过程对不对（专业域特有）
④ 表达适当性：格式是否完整、语言是否符合用户角色
```

**"过程正确性"是专业域独有的评测维度**，也是最容易漏掉的。答案对但过程错，在财税领域是不可接受的。

### 11.3 评测执行方式

| 层 | 方式 | 频率 |
|---|---|---|
| 自动评测 | 引用存在性、效力状态、计算复算（规则类，可100%自动） | 每次变更 |
| 半自动 | LLM 裁判比对标准答案要点 | 每次变更 |
| 人工 | 抽检 5% + 全部"一票否决"失败样本 | 每次发布 |
| 专家评审 | 重大政策变化后，由税务师评审 | 按需 |

### 11.4 门禁与发布（三道闸，分域阈值）

```
闸门 1 离线回归（分域评测集）→ 一票否决项必须全通过
闸门 2 影子流量 → 新旧答案对比，专家抽检
闸门 3 灰度放量 5% → 20% → 50% → 100%

任一阶段触发：效力错误 / 计算错误 / 投诉激增 → 立即回滚
```

## 12. 部署与运维

部署拓扑（Nginx + FastAPI 多实例 + PG 主从 + Qdrant 3 节点 + Redis + Celery + Embedding 服务）沿用不变，并增加两项：

### 12.1 域级灰度

```yaml
灰度维度：
  - 按租户：先在 1 家客户启用新域包
  - 按知识批次：新导入的法规先以"仅内部可见"运行观察
  - 按功能：新增"政策变化提醒"先在 10% 租户开启
```

### 12.2 专业域特有的监控项

| 监控项 | 告警条件 | 含义 |
|---|---|---|
| 效力校验拦截率 | 突增 | 可能引用了过期文件，或监控漏了新政策 |
| 计算器调用失败率 | > 1% | 计算引擎异常 |
| 政策变更未处理数 | 积压 > 20 | 时效风险 |
| 专家复核队列长度 | 积压 > 50 | 处理能力不足 |
| 免责声明渲染失败 | 任何一次 | 合规风险，立即修复 |
| **红线命中次数** | 任何一次（需人工确认） | 有人在试探违法方案，需评估话术与风控 |
| **高风险方案误放次数** | 任何一次 | 严重合规事故，立即排查 |

### 12.3 双形态部署：SaaS + 私有化

| 维度 | SaaS 形态 | 私有化形态 |
|---|---|---|
| 面向 | 中小企业、快速试用 | 大型企业、集团、对数据敏感客户 |
| 租户隔离 | 多租户共享（payload 过滤 + RLS） | 单客户独占实例 |
| 数据位置 | 平台侧 | **客户内网，数据不出域** |
| LLM 调用 | 平台统一调用境内模型 API | 可选本地部署模型（成本高但数据不出域） |
| 财税数据 | 加密存储 + 最小化收集 | 全量留在客户侧 |
| 更新方式 | 平台统一升级 | 提供升级包与版本管理（客户可锁定版本） |
| 成本 | 低（共享） | 高（独占资源 + 部署实施） |

**架构上的要求（为了两种形态共用一套代码）**：

1. **模型接入可替换**：SaaS 用云端 API，私有化用本地推理，通过 Provider 抽象切换
2. **存储可分离**：组件全部容器化，私有化时用客户自己的 PG / Qdrant / Redis
3. **无外部强依赖**：私有化环境不能依赖平台侧的专有服务
4. **许可证与授权**：私有化需要授权文件机制（控制版本、有效期、模块开关）
5. **配置驱动**：域包、模型地址、密钥、开关全部走配置，不打进镜像

**代价要提前知道**：双形态意味着**每个功能都要测两遍**，私有化版本的升级与支持成本显著高于 SaaS。建议：SaaS 作为主推，私有化按客户规模定制交付。

### 12.4 对外接口预留（首版独立，预留接口）

首版不接入客户现有系统，但接口要提前定义好，避免后期改造成本。

| 接口 | 方向 | 用途 |
|---|---|---|
| `POST /api/v1/qa/ask` | 入 | 业务系统调用问答（带租户、会话、角色） |
| `POST /api/v1/planning/analyze` | 入 | 提交企业画像，返回筹划方案（异步，返回任务 ID） |
| `GET  /api/v1/planning/tasks/{id}` | 入 | 查询方案生成/复核进度 |
| `POST /api/v1/calc/tax` | 入 | 税费计算（供客户系统直接调用） |
| `POST /api/v1/knowledge/documents` | 入 | 推送法规或内部资料入库 |
| `GET  /api/v1/citations/{id}` | 入 | 查询引用条款的完整信息与原文 |
| `POST /webhook/policy-change` | 出 | 政策变化提醒推送 |
| `POST /webhook/review-result` | 出 | 专家复核结果通知 |
| `POST /webhook/answer-feedback` | 出 | 答案反馈事件 |

**接口设计要点**：

- **版本化**（`/v1/`），避免未来破坏性变更
- **鉴权**：租户级 API Key + 权限 scope
- **幂等**：写操作带幂等键
- **限流**：按租户配额
- **异步优先**：筹划这类耗时操作必须异步（返回任务 ID + 回调），不要同步阻塞
- **事件推送**：用 Webhook 而不是轮询，并支持验签与重试

## 13. 成本模型

按"日活 1000 用户、日提问 1 万次"估算。

| 项目 | 月成本估算 | 说明 |
|---|---|---|
| LLM 生成 | 800～2500 元 | 专业域上下文更长（法规原文 + 知识），token 消耗较大 |
| LLM 抽取（知识入库） | 300～800 元 | 法规条文抽取，一次性 + 增量 |
| Embedding | 0～200 元 | 本地推理约 0 |
| Rerank | 0（本地方案） | 用 API 会显著上升 |
| 计算引擎 | 0 | 自建，仅 CPU |
| 验证层 | 100～300 元 | 一致性检查需 LLM |
| **筹划引擎** | **600～2000 元** | 方案空间生成本身要多次调用模型，且上下文含企业画像与多份法规，单次成本显著高于普通问答 |
| 评测 | 200～500 元 | 专业评测集大，评测成本较高 |
| 服务器 | 1500～3000 元 | 3 节点集群 + 2 台应用 + 数据库 |
| **合计** | **约 4000～9000 元/月** | 不含专家审核人力 |

**隐性成本必须提前说明**：

| 隐性成本 | 说明 |
|---|---|
| 专家审核 | 财税法规需要专业人士把关，这是最大的隐性成本 |
| **筹划专家复核** | 🟡🔴 级方案需税务师复核。按每方案 10～20 分钟计，若日均 20 个筹划请求，需要约 3～6 小时/天的专家投入 |
| 知识维护 | 财税政策持续更新，需要长期维护（每周数小时） |

**控制手段**：优先做高频、高价值的知识；低频领域用"暂不支持"明确边界，不要什么都想覆盖。

## 14. 模块建设顺序与验收标准

前提：**先把财税域做深**。

| 模块 | 内容 | 参考工期 | 验收标准 |
|---|---|---|---|
| **0 基础设施** | Docker 环境、项目骨架、日志、健康检查 | 3～5 天 | 依赖全部就绪，健康检查通过 |

| **2 域包框架** | 域包加载、注册、路由；本体 Schema 定义 | 1 周 | 能加载域包；路由能正确分辨财税问题 |
| **3 财税知识结构化** | 法规导入、条文切分（章条款项）、文号识别、效力状态、版本区间、关系构建 | 2 周 | 导入 100 份法规，条文层级正确率 ≥ 95%，版本区间无重叠 |

| **5 推理与计算** | 事实抽取、适用性判定、计算引擎（增值税+附加）、答案模板 | 2 周 | 20 道典型税务计算题全部算对，且给出完整依据 |
| **6 验证层** | 引用验证、时效验证、计算复算、合规校验 | 1 周 | 故意注入废止条款，系统能拦截 |
| **7 筹划引擎** | 手法库建设、企业画像抽取、方案空间生成、四道合法性检查、风险分级、多方案对比、专家复核台 | 2.5 周 | 红线路障测试 100% 拦截；🟢 方案可直达用户，🔴 方案被拦在复核台 |
| **8 自进化** | 知识抽取流水线、政策变更监控、缺口发现、衰退淘汰 | 1.5 周 | 模拟一次政策修订，系统能自动标记受影响知识 |
| **9 评测与门禁** | 财税评测集 300 条（含筹划 200 条）、自动评测、三道闸、回滚 | 1.5 周 | 故意导入错误知识，门禁能阻断发布 |
| **10 前端与后台** | 问答界面（结构化渲染）、引用卡片、计算过程展示、方案对比表、专家复核台、管理后台 | 1.5 周 | 端到端可用，可交付试用 |

**参考工期**：

- 全部模块：约 **15～18 周**，含问答、计算、验证、筹划、自进化、门禁与界面

> 说明：筹划引擎使工期增加约 2.5 周，主要成本在**手法库建设**（需要专家把七类手法的适用条件、滥用边界、被否案例逐条写清楚），而非编码。

**两个关键检查点**：

- **第 5 模块完成**：能演示"给出计算过程和依据"的财税问答，此时可以找真实用户验证价值
- **第 7 模块完成**：能演示筹划方案对比，且红线路障全部拦截

## 15. 风险登记

| # | 风险 | 影响 | 概率 | 应对 |
|---|---|---|---|---|
| R1 | **引用了已失效的法规** | 极严重 | 中 | 效力验证一票否决 + 政策变更监控 + 版本区间模型 |
| R2 | **计算错误** | 极严重 | 低 | 计算引擎强制复算，禁止模型心算；规则版本化 |
| R3 | 答案正确但计算步骤错误 | 高 | 中 | 步骤级评测 + 计算引擎逐步复算 |
| R5 | 法规数据获取困难或版权问题 | 高 | 中 | 优先用官方公开渠道；必要时只存摘要 + 链接 |
| R6 | 专业知识维护跟不上变化 | 高 | 高 | 政策变更监控 + 专家复核队列 + 明确"知识截至日期" |

| R11 | 领域本体设计不足，后期难扩展 | 高 | 中 | 本体定义由业务专家参与评审 |
| R12 | LLM 成本随上下文增长超预算 | 中 | 中 | 上下文压缩 + 只送命中条文而非整部法规 + 缓存 |
| R13 | **筹划方案被认定越界或违法** | 极严重 | 中 | 四道检查 + 红线清单 + 🔴 强制专家复核 + 红线事件留痕 |
| R14 | 筹划建议被采纳后产生税务争议 | 高 | 中 | 强制免责 + 全链路留痕 + 要求用户填写真实商业目的 + 导出件带版本 |

| R17 | 专家复核积压导致用户等待 | 中 | 高 | 分级复核 + 明确响应时限 + 排队状态可视化 + 超时自动降级标注 |

### 16.2 需要业务方提供的资源

| 资源 | 用途 | 缺失的后果 |
|---|---|---|
| 一批真实的财税法规文件 | 建立首批知识库 | 无法验证抽取质量 |
| 财税专家（税务师/资深会计） | 审核知识、制定判定规则、评审答案 | 系统可能"看起来对但实际错" |
| **财税专家用于筹划复核算力** | 🟡🔴 级方案的复核、手法库的滥用边界与案例编写 | 筹划功能无法达到可用标准，或存在越界风险 |

| 首批评测题目（各 100 条真实问题） | 建立评测基线 | 无法衡量质量 |

## 附录 A：术语说明（给非技术背景阅读）

| 术语 | 一句话解释 |
|---|---|
| **领域本体** | 把一个专业领域的知识结构写清楚，比如"法规分章、章下有条款项" |
| **域包** | 某个行业的完整配置包（结构 + 规则 + 模板 + 法规数据），像装软件一样装进系统 |
| **推理层** | 系统"动脑筋"的地方：判断适用条件、选解法、算结果，而不是只把资料找出来 |
| **验证层** | 生成答案后，用程序逐项检查"引用真不真、有没有过期、算得对不对" |
| **时效/时间旅行** | 每个条文记录"从哪天生效、到哪天失效"，可以查出任意历史时点当时的规定 |
| **效力状态** | 一份文件现在是"现行有效 / 已废止 / 尚未生效 / 部分废止" |
| **条件判定树** | 把"什情况下适用哪条规则"写成树状判断流程，逐条判断 |
| **RRF 融合** | 把几路搜索结果按"排名"合并，而不是按分数相加，更稳 |
| **门禁** | 上线的关卡，测试不过就不许发布 |
| **影子流量** | 新版本处理真实请求但不给用户看，只用来对比效果 |
| **一票否决** | 某项指标只要有一条不合格，整批就禁止发布 |
| **筹划** | 在法律允许范围内，通过合理安排降低税负或递延纳税（合法的省钱安排） |
| **方案寻优** | 不是找一个答案，而是在可行范围内比较多个方案，选最合适的 |
| **合理商业目的** | 税法上的关键标准：做这项安排主要是因为经营需要，而不是主要为了少缴税 |
| **实质重于形式** | 税务机关看交易的实质，而不只看合同怎么写。纸面安排没有真实业务会被否定 |
| **红线清单** | 明确列出绝对不能碰的违法做法，系统一旦识别就拒绝并给出合规替代 |
| **风险分级** | 把方案分成稳健🟢 / 审慎🟡 / 高风险🔴，不同等级用不同的输出规则 |
| **涉税专业服务** | 向他人提供的税务咨询、税收策划等服务，在中国有相应的监管与资质要求 |
| **被否案例** | 真实案例中曾被税务机关否定的做法，用来约束系统不要生成类似方案 |
