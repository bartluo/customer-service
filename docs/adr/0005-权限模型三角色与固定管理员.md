# ADR-0005：权限模型采用三角色 + 动态授权 + 固定管理员

**状态**: accepted
**日期**: 2026-09-29
**决策者**: 用户

## 背景

原文技术方案第 10.1 节列了 8 个角色（企业用户、会计/税务人员、税务专家、知识管理员、管理员、
学生、教师、家长）。最终确定简化为**动态管理**：

> 角色和人员采取动态管理方式，首先设计三个角色：管理员、审核专家、客户。
> 管理员固定，管理员可以给用户设定权限。

## 决策

1. **财税首版只设三个内置角色**：`admin`（管理员）、`reviewer`（审核专家）、`client`（客户）。
   三个角色由系统预置、不可删除；后续要加角色是数据变更，不改代码。
2. **人员不写死**：用户全部在后台动态创建，角色与权限动态分配。
3. **固定管理员**：系统内置唯一受保护账号，拥有全部权限，不可删除/停用/降权。
   它只用于初始化与兜底，日常管理交给普通管理员。
4. **两级授权**：管理员可给用户分配"客户"角色与客户类权限；
   **"审核专家"角色与业务审核类权限只能由固定管理员授予**。
5. **授权一律留痕**：谁在什么时候给谁加了什么权限，写进审计日志且不可删除。
6. **分权**：管理员默认不参与业务审核（不能自己审知识、自己放行高风险方案）；
   审核专家默认看不到客户全量数据，只看到进入复核流程的那部分。

## 考虑过的其他方案

**方案 A：保留 8 个角色，按岗位分配**
- 优点：贴近传统企业权限模型，直观
- 否决原因：已明确要三个角色；且岗位与权限高度重叠，维护两套概念反而容易配错

**方案 B：不做角色，只按人逐个勾权限**
- 优点：最灵活
- 否决原因：新人入职要勾几十个权限项，容易漏配；审计时也说不清"这个人应该有什么权限"

**方案 C：角色写死在代码里**
- 优点：实现最简单
- 否决原因：要的是动态管理，未来加"合规官"之类的角色不该改代码、不该重新发版

## 后果

**正面**

- 新增人员 = 建用户 + 选角色，30 秒完成；特殊需求再单独加权限。
- "会计用计算器底稿"这类诉求不需要新角色，给客户账号单独加 `calc.draft.save` 即可。
- 固定管理员账号存在，永远不会出现"管理员全被删掉、系统没人能进"的死局。
- 分权 + 留痕，使系统在财税这种高责任场景下能自证"谁做的决定"。

**负面 / 需要留意**

- 审核专家角色的授予集中在固定管理员身上，人手少时他会成为瓶颈（可用流程约定缓解）。
- 每个用户都要维护一条租户归属，数据模型比"只有一张 users 表"复杂一些。
