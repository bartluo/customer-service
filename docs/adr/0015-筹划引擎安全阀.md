# ADR-0015 筹划引擎：安全阀先于方案生成

- 状态：已采纳（accepted）
- 日期：2026-10-01
- 决策者：项目负责人

## 背景

筹划与普通问答有一个本质区别：**筹划最严重的失败模式是"给出违法方案"**。
问答答错是"信息不准"，筹划答错是"用户照着做，构成违法"。

所以这一阶段的建设顺序刻意与直觉相反：**先建安全阀，后建方案生成**。

## 决策

### 一、先做画像、手法库、红线与四道检查，最后才做方案生成

技术方案 4.10 的六段流水线里，第 ⑤ 段"合法性审查"是安全阀。
按直觉会先做第 ② 段"筹划空间生成"（看着更"像产品"），
但那会得到一个**能生成方案、却拦不住违法方案**的系统——
而这类系统一旦上线，造成的损害比"没有筹划功能"大得多。

所以本阶段第一批交付的是：企业画像、手法库、红线清单、四道检查、风险分级。

### 二、红线清单是硬规则，不是提示词

红线写在 `domains/finance_tax/risk_rules.yaml`（域包只能加严不能放宽），
识别用正则规则表，不用模型。

理由：红线判断事关法律责任，必须**可审计、可复现、可回归测试**。
模型更适合识别"换了说法"的同类诉求，作为补充而非主力——
这一半留作扩展点（规格里写的也是"规则匹配 + LLM 判定"）。

**但识别模式不能写得太窄**。实测中踩到：`不(?:入账|记账)` 匹配不了"**不想**入账"，
`关联.{0,8}(?:定价|交易).{0,10}(?:避税|少缴)` 匹配不了"关联交易定价把利润**转到低税率**公司"。
口语里这类插入与换词极其常见，模式必须留出余量。
同时反向也要测：**正常咨询不能被误拦**（"怎么合理安排开票时间"不是虚开）。

### 三、拒绝时必须给替代路径

技术方案 4.12 专门强调这一点：不是冷冰冰地说"不能回答"，而是

> 这个做法属于 X 类违法风险 → 风险在于 Y → 如果您的目的是 Z，合规的做法是……

用户来找筹划，本质是想要合法的省钱办法。**只拒绝不给路，等于把用户推向更野的中介。**
所以每条红线都配了一段替代路径，写死在代码里并随命中一起返回。

### 四、反避税检查：不替用户编商业目的

"合理商业目的"是抽象标准，容易被做成形式主义。做法是三道问句：

1. 如果完全没有税收利益，这项安排还会做吗？
2. 这项安排带来什么真实经营效益？
3. 有哪些可验证的业务证据？

**用户填不出来，这件事本身就是风险信号**——系统不替他编，
而是把这项判为不通过、风险升到 🟡。

### 五、业务真实性只能由用户确认

实质检查里 `business_authentic` 必须由用户确认为真。
这一项**不确认就是作废（🔴）**，因为没有真实业务实质的筹划就是红线的起点。
系统没有能力、也没有资格替用户确认这件事。

### 六、手法库的"滥用边界"与"被否案例"是一等公民

每条手法必须写齐六字段，其中"滥用边界"与"被否案例"是**普通资料里没有的东西**：
同一手法在合规使用和滥用之间只差一条线，把这条线写出来，
系统才能在方案里自动附上"这样用合法，一旦 X 就违法"的提示。

导入时校验"滥用边界不能为空"——它是这套资产最核心的价值，空着就等于没写。

### 七、手法素材未经专家确认不得用于出方案

素材以 `draft`（待专家确认）状态入库，`TechniqueLibrary(include_draft=False)`
是出方案时的正确用法。这对应手法素材的要求：
**手法素材必须由内部专家提供并确认**。

## 后果

- 红线识别：8 类全部可拦，且每条都带替代路径；正常咨询不被误拦。
- 四道检查：每道都有一个失败案例能把方案拦下；全通过才判 🟢。
- 风险分级：🔴（红线/依据不成立/真实性未确认）→ `review_only`，不直达用户；
  🟡（反避税有缺项/风险偏好进取）→ 带提示输出 + 强制专家复核；🟢 → 直接输出。
- 筹划总开关 `planning_enabled` 保持 **false**：资质主体（F2）落实前不对外提供。
- 新增测试 30 项，后端测试总数 395 项全绿。

## 补充约定

### 三路生成，信息不足也要给

手法类别决定走哪条路径：政策适用型 → A，主体架构/业务模式/资产投资/区域 → B，
时点安排/递延 → C。**"不适用"的手法不出方案，"信息不足"的照样出，但标出缺什么。**

筹划里"信息不足"太常见了（不知道能不能改合同、不知道从业人数）。
直接丢掉等于什么都没给；标出来用户才知道补什么。

### 测算的一条硬约束：算不出来就说算不出来

数字全部来自计算引擎（复用既有引擎，为筹划补了企业所得税规则：
30 万应纳税所得额，25% 基本税率 7.5 万 → 小微优惠实缴 1.5 万，节税 6 万）。

研发加计、设备一次性扣除这类"按实际发生额算"的优惠，画像里没有对应金额，
对比表里明确写"需补充研发费用金额后测算"，**不给一个看起来精确、其实靠猜的数字**。
这类数用户会直接拿去决策。

### 对比表要能回答"先做哪个"

所以除了节税效果，还要有风险、实施成本、建议与**组合提示**
（哪些能叠加、哪些必须一起评估、哪些要等别的方案稳定后再动）。
只给一个方案清单等于没帮用户做决策。

## 补充约定：复核台与高风险不外泄

### 分流不是"过滤列表"，而是两条互斥通道

`dispatch()` 返回的不是一个过滤后的列表，而是 `user_facing` 与 `review_queue`
两条显式分开的通道——**调用方拿不到"忘记过滤"的机会**。

里面还留了一道兜底：如果 🔴 意外混进了给用户的列表，分流这一步会把它揪出来
并记入日志。不假设上游一定传对了。

分级的准确含义也容易被写错，这里明确一次：

| 等级 | 给用户？ | 送专家？ |
|---|---|---|
| 🟢 稳健 | 是 | 事后抽检 |
| 🟡 审慎 | **是（带提示）** | 是（限时确认） |
| 🔴 高风险 | **否** | 是（唯一出口） |

🟡 与 🔴 必须分开表达：把 🟡 也算成"已拦截"，等于让用户少拿到方案——
**"送专家复核"不等于"不发给你"**，这两件事必须分开表达。

### 复核台的一屏看清，靠的是"快照"不是"重算"

复核记录里存的是**当时的画像与方案快照**，不是事后重新生成的结果。
刻意如此：专家要审的是"用户实际收到的那份"，重算出来的东西
会因为知识库或规则变动而不同，反而对不上账。

同理，`delivered_to_user` 字段是"高风险不外泄"的落库凭证——
事后能查"这条到底有没有给用户看过"。

### 反馈入库：只整理，不自动写进手法库

驳回与修改后放行会整理成**待转清单**（驳回 → 评测负样本；修改 → 校准验证器松紧），
但**不自动追加到手法库的"被否案例"**。手法库是专家资产，
自动写入会让未经确认的判断混进权威数据。
要不要收进去，由专家决定。
