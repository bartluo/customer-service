# ADR-0018 单份法规索引重建：发布与下架必须秒级一致

- 状态：已采纳（accepted）
- 日期：2026-10-02
- 决策者：项目负责人

## 背景

原有的索引写入只有一个动作：**全量重建**（`index_articles`，先清空该域再全量写入）。

在 CPU 上全量重建要十几分钟。而下面这些事件每天都在发生：

- 审核专家发布 / 驳回一份法规
- 有效性核查把某份法规标成废止
- 执行期限届满，某份公告失效

全量重建的直接后果是**索引长期落后于数据库**：数据库里已经废止的条文，
在索引重建完成之前仍然能被检索到。这正是财税场景最不能接受的一类错误——
用户拿着废止条款去申报。

验收门 G9-D 把这个问题摊开了：要"故意导入一条错误知识看门禁拦不拦得住"，
结果发现**注入进去的法规根本查不到**——它在时效治理时索引点就被删了（ADR-0012），
只改数据库状态补不回来。

## 决策

新增 `reindex_regulation(db, regulation_id, client=None)`：
**只重建一份法规的索引点，先按 `regulation_id` 删旧点，再按当前数据库状态写入。**

口径与全量构建完全一致（只索引 条/款/项、只索引 published、
只索引 `effective`/`partially_repealed`），所以它不会成为"绕过红线"的旁路。

三个要点：

1. **先删后写，不能只 upsert。**
   upsert 只覆盖同 ID 的点；某一条被单独废止时，条目数变少，
   旧点会被留在索引里继续被检索到。删除这一步不能省。

2. **没有可索引条目时，删点就是正确动作。**
   法规被驳回或被整体废止 → 构建结果为空 → 把它的点删干净，
   索引里就不该有这份法规。这不是"没数据所以跳过"。

3. **向量服务不可用时保留索引原样。**
   宁可"索引是旧的"，也不能删成"索引是空的"——
   旧索引只是不新鲜（还能查、只是可能少一条），空索引是全部查不到。
   这一点与全量重建的前置探活是同一个道理（ADR-0007）。

同时导出 `remove_regulation_points(regulation_id)`，用于撤回 / 下架。

## 后果

- 法规状态变更可以**即时**同步到索引，不再等十几分钟的全量重建。
- 验收门 G9-D 得以成立：注入时用真实路径把错误知识灌进索引
  （改主表 + 改条文版本表 + 重建该份法规索引），
  还原时用同一条路径把点删干净。
- 新增测试锁住三个往返：写 → 覆盖（不产生重复点）→ 改回废止后再重建必须查不到；
  以及条文数变少时旧点必须消失。

## 实现要点

- **只改法规主表是没用的**。检索过滤与检索后的权威复核看的都是
  `RegulationArticleVersion.effect_status`，只改 `Regulation.effect_status`
  等于没改。
- **还原必须删点**。只把状态改回去不够：注入时补进去的索引点会留在库里，
  会造成"已废止条文可被检索"。

## 已知限制

- 全量重建仍然是"兜底动作"（`scripts/build_vector_index.py`），
  适合大规模数据修复，不适合单条变更。
- 单份重建是同步阻塞调用，发布接口目前是同步等它返回（单份耗时约 1～2 秒）。
  法规批量导入时不要逐份调用，走全量重建。
