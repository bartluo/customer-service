# ADR-0014 验证层：引用一票否决、时效第二道防线、数字必须复算

- 状态：已采纳（accepted）
- 日期：2026-10-01
- 决策者：项目负责人

## 背景

本决策落地技术方案第 6 章。规格把这一层的必要性说得很直白：

> 普通客服答错了，用户顶多不满意。专业域答错了，后果是补税、滞纳金、罚款、信用降级。
> **"生成完就直接返回"在专业域不可接受。**

落地时有几处必须定的口径。

## 决策

### 一、引用错误一票否决，而且**给了文号就只按文号核对**

引用错误是"编造依据"，比算错更严重——它伪造了权威性。
用户看到"财税〔2020〕99999号 第三条规定……"，不会怀疑这份文件根本不存在。

实现上有一条容易写错的细节：**文号查不到时，不能退回按标题匹配**。
如果退回了，伪造的文号只要标题对得上就能蒙混过关——而这恰恰是引用验证要拦的头号问题。
（注意：若写成"文号找不到再按标题找"，伪造的文号会全部漏过。）

### 二、时效是独立的第二道防线，不假设上游做对了

检索层已经做了效力硬过滤，验证层**再查一遍**。看似重复，但两者失败的后果不同：
检索漏过滤是"召回错了"，验证漏查是"错的答案发出去了"。

检查项按规格：废止 / 被替代 / 草案 → 阻断；尚未生效 → 除非答案里说明了施行时间，
否则阻断；有效区间不覆盖问题时点 → 阻断。

### 三、数字必须复算，且属于"可自动修正"

计算引擎保证"引擎算得对"，但**答案里的数字不一定来自引擎**——
可能被模型改写、被中间步骤篡改、或是上一版答案的残留。
所以答案里的每个金额都要拿引擎重算一遍比对。

不一致归为**可修正**（不是直接丢弃）：数字笔误没必要让用户等一次重新生成，
直接用引擎结果替换、重新验证即可。记录里仍会标成 `fixed`，
复核时能看出"这条答案被改过"。

### 四、免责声明由模板渲染，验证器只检查它在不在

免责段来自答案模板的 `fixed_text`，不依赖任何调用方传值。
验证器检查的是**渲染后的段落**，不是组装前的原始内容——
拿原始内容去验会把本来正确的答案误判成"缺免责段"。

### 五、越界表述用规则表，不用模型判

"保证通过""一定能""不用交税""税务机关一定会"这类表述是有限且已知的，
规则表可审计、可维护、零成本、结果可复现。模型判这类问题只会引入不确定性。

## 失败处理（规格 7.3 的落地）

| 情况 | 处理 | 实现 |
|---|---|---|
| 只有可修正问题（数字不符） | 就地修正 → 重新验证 → 输出 | `_apply_fixes` |
| 有阻断问题（假文号、废止条文） | 剔掉问题引用 → 重新生成 → 最多 2 次 | `rebuild` 回调 |
| 修不回来 | **降级输出**：说明"已找到政策但未通过验证"，附候选条款 | `_degraded_sections` |

**关键原则：宁可说"不确定"，也不输出未通过验证的结论。**

## 验证记录（规格 7.4）

新增 `verification_records` 表（迁移 `7a3f2c8e5b41`），每次验证写一条：
结论、是否通过、重试次数、各验证器明细、命中的原因码。

用途是**找系统性问题**：引用验证拦截率短期内上升，
说明知识库质量出问题了，比等用户投诉早得多。

写记录失败不影响答案输出——记录是为了改进，不是交付的一部分。

## 后果

- 验收门 G6：**人为注入 20 个错误（8 个假文号、6 个不可用条文、6 个错金额），
  拦截率 100%**；`scripts/verify_validation.py` → 7/7 通过。
- 正常答案仍然能通过验证（防止"验证器把对的也拦了"，这是同一条验收里的 B1 项）。
- 问答主链路已接入验证层：答案组装完 → 送检 → 通过才返回。
- 新增验证层测试 18 项，后端测试总数 365 项全绿。
