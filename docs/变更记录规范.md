# 变更记录规范

为了让每一次升级都可追溯，本项目按下面的规则记录变更。

---

## 一、版本号

采用语义化版本 `主版本.次版本.修订号`：

| 位 | 什么时候加 | 例子 |
|---|---|---|
| **主版本** | 有不兼容的变更：接口协议、数据表结构、配置项改名 | 1.0.0 → 2.0.0 |
| **次版本** | 新增功能，向后兼容 | 1.0.0 → 1.1.0 |
| **修订号** | 修问题、改文案、调参数 | 1.0.0 → 1.0.1 |

---

## 二、改一次记一次

每一处影响使用者或部署的改动，都要在 [CHANGELOG.md](../CHANGELOG.md) 里记一条，
按下面六类归档：

| 分类 | 放什么 |
|---|---|
| 新增 | 新功能、新接口、新配置项 |
| 变更 | 现有行为的调整（原有用法通常仍可用） |
| 废弃 | 即将移除的能力 |
| 移除 | 已移除的能力 |
| 修复 | 修掉的问题 |
| 安全 | 安全相关的修补 |

**写法**：一句话说清"改了什么、对使用者有什么影响"。

**不写**：内部代号、开发批次、调试过程。

---

## 三、什么时候写 ADR

满足任一条，就补一份 ADR 放进 `docs/adr/`：

1. 选了某个方案，同时放弃了别的方案（例如对象存储选型）
2. 定了一条以后不能随便改的口径（例如效力状态枚举、税种标注）
3. 做了一处与《技术方案》的有意偏离

ADR 是**决策记录**：一次写清背景、决定、后果即可。
后续若有调整，**另起一份新 ADR**，不修改原文件——这样能保留完整的决策轨迹。

---

## 四、不记什么

- 代码内部整理（重命名变量、调整注释），除非影响对外行为
- 调试过程与试错记录
- 还没进入正式版本的功能草稿

---

## 五、发布流程

1. 把本版要记的内容写进 `CHANGELOG.md` 的「未发布」段
2. 涉及架构口径的改动 → 补一份 ADR
3. 跑验收：各 `scripts/verify_*.py` 与后端测试
4. 发布时把「未发布」改成版本号与日期，并新建一个空的「未发布」段
5. 打标签：`git tag -a v1.1.0 -m "v1.1.0"`，再 `git push --tags`
